# Бизнес-требования. Часть 1

> **Тема:** текущие бизнес-возможности системы SnowSolution  
> **Статус:** черновик по результатам анализа исходного кода  
> **Основание:** поведение, явно представленное в исходниках проекта. Это описание текущего объёма, а не подтверждённая заказчиком целевая модель.

## 1. Цель и границы

Система предоставляет защищённый вход к сервису бизнес-процессов и позволяет запустить процесс, просмотреть активные задачи и завершить задачу. Экземпляры процессов и задачи обрабатываются средствами процессного движка. Отдельный сервис обнаружения поддерживает связь между шлюзом и сервисом процессов.

В этой части описаны только возможности, для которых найдены прямые подтверждения в коде:

- запуск экземпляра зарегистрированного бизнес-процесса;
- просмотр списка активных задач;
- завершение задачи;
- доступ к операциям через API-шлюз с проверкой JWT;
- передача идентификатора и имени пользователя в заголовках запроса к сервису;
- публикация документации API.

Не включены неподтверждённые пользовательские функции: создание/редактирование схем процессов, назначение задач, управление ролями, просмотр истории, загрузка бизнес-данных и отчётность.

## 2. Основание и охват обследования

- **Метод обследования:** просмотр контроллера процессов, правил безопасности шлюза, маршрутов API, моделей BPMN, настроек обнаружения сервисов и тестов.
- **Обнаруженные модули:** шлюз API (`api-gateway`), сервис обработки бизнес-процессов (`process-engine-service`), сервер обнаружения сервисов (`eureka-server`).
- **Операции API процессов в охвате:** 3 — запуск процесса, просмотр задач, завершение задачи.
- **Пределы доказательности:** тесты подтверждают запуск контекста приложения, но не проверяют бизнес-операции; один BPMN-процесс представляет задачу согласования, другой — шаг проверки данных с делегированным обработчиком. Подробные правила бизнеса по этим процессам из кода не следуют.

## 3. Участники и заинтересованные стороны

- **Авторизованный пользователь/клиент:** обращается к операциям процессов с действительным токеном.
- **Оператор процесса:** просматривает активные задачи и инициирует завершение выбранной задачи. В коде нет отдельной роли оператора или проверки назначения задачи.
- **Сопровождающая команда:** использует документацию API и состояние сервисов для сопровождения решения.
- **Сервис процессов:** исполняет определения процессов и предоставляет операции над задачами.

## 4. Пользовательские сценарии

### Сценарий 1 — Запуск процесса (P1)

Пользователь запускает зарегистрированный процесс по его ключу и получает идентификатор созданного экземпляра, чтобы дальнейшая работа могла быть связана с этим запуском.

**Обоснование приоритета:** запуск создаёт экземпляр процесса и является начальной точкой основного сквозного сценария.

**Независимая проверка:** передать известный ключ процесса через защищённый API-шлюз и проверить успешный ответ с идентификатором экземпляра.

**Критерии приёмки:**

1. **Дано** действительный JWT и зарегистрированное определение процесса, **когда** клиент отправляет запрос запуска с ключом процесса, **тогда** система запускает экземпляр и возвращает его идентификатор.
2. **Дано** действительный JWT и неизвестный/непригодный ключ процесса, **когда** клиент запрашивает запуск, **тогда** система не сообщает об успешном запуске и возвращает ошибку.

### Сценарий 2 — Просмотр активных задач (P1)

Оператор получает перечень текущих задач, чтобы определить, какие действия ожидают выполнения.

**Обоснование приоритета:** без списка задач невозможно выбрать задачу для последующего завершения в имеющемся API.

**Независимая проверка:** выполнить запрос списка при наличии активных задач и сверить идентификатор задачи, название, исполнителя и идентификатор экземпляра процесса.

**Критерии приёмки:**

1. **Дано** действительный JWT, **когда** клиент запрашивает список задач, **тогда** ответ содержит активные задачи с идентификаторами задач и экземпляров процесса.
2. **Дано** задача без указанного названия или исполнителя, **когда** она включается в ответ, **тогда** название представлено пустым значением, а исполнитель — значением «Unassigned».
3. **Дано** активных задач нет, **когда** клиент запрашивает список, **тогда** система возвращает пустой список.

### Сценарий 3 — Завершение задачи (P1)

Оператор завершает выбранную активную задачу, чтобы продолжить ход процесса.

**Обоснование приоритета:** завершение задачи — единственное явно предоставленное действие над активной пользовательской задачей.

**Независимая проверка:** запустить процесс с пользовательской задачей, завершить её по идентификатору и проверить, что задача больше не активна.

**Критерии приёмки:**

1. **Дано** действительный JWT и активная задача, **когда** клиент отправляет запрос завершения для её идентификатора, **тогда** задача завершается и система возвращает подтверждение.
2. **Дано** неизвестный или уже завершённый идентификатор, **когда** клиент отправляет запрос завершения, **тогда** система не должна подтверждать успешное завершение; формат и содержание ошибки требуют отдельного согласования, поскольку сейчас явно не определены контроллером.

### Сценарий 4 — Защищённый доступ к API (P1)

Клиент обращается к бизнес-операциям через единый шлюз; доступ к защищённым маршрутам предоставляется после аутентификации по JWT.

**Обоснование приоритета:** все прикладные операции доступны через шлюз и требуют аутентификации.

**Независимая проверка:** сравнить запрос к прикладному маршруту без JWT и с действительным токеном; отдельно проверить доступность документированных исключений.

**Критерии приёмки:**

1. **Дано** запрос к защищённому маршруту без действительной аутентификации, **когда** запрос поступает в шлюз, **тогда** бизнес-операция не выполняется.
2. **Дано** запрос с проверенным JWT, **когда** запрос проходит через шлюз, **тогда** шлюз передаёт целевому сервису идентификатор пользователя и имя пользователя, если соответствующие сведения присутствуют в токене.
3. **Дано** запрос к разрешённому маршруту документации, **когда** он отправлен без JWT, **тогда** шлюз не требует аутентификацию для этого маршрута.

## 5. Функциональные требования

- **REQ-001:** Система должна принимать запрос на запуск процесса по ключу определения процесса.
- **REQ-002:** При успешном запуске система должна возвращать идентификатор экземпляра процесса.
- **REQ-003:** Система должна предоставлять список активных задач.
- **REQ-004:** Для каждой задачи в списке система должна предоставлять идентификатор задачи, название, исполнителя и идентификатор экземпляра процесса.
- **REQ-005:** Для задачи без названия система должна возвращать пустое значение названия; для задачи без исполнителя — значение «Unassigned».
- **REQ-006:** Система должна позволять запросить завершение задачи по её идентификатору.
- **REQ-007:** При успешном завершении задачи система должна возвращать подтверждение выполнения операции.
- **REQ-008:** Система должна требовать аутентификацию JWT для прикладных маршрутов, не входящих в явно разрешённые маршруты документации и мониторинга.
- **REQ-009:** Для аутентифицированного запроса шлюз должен передавать целевому сервису идентификатор пользователя и имя пользователя из JWT, если они присутствуют.
- **REQ-010:** Система должна предоставлять доступ к документации API без аутентификации по разрешённым маршрутам.
- **REQ-011:** Шлюз должен направлять запросы API процессов в сервис процессов, используя регистрацию и обнаружение сервисов.

## 6. Ключевые бизнес-сущности

- **Определение процесса:** описание исполняемого бизнес-процесса, запускаемого по ключу. В проекте присутствуют примеры согласования и проверки данных.
- **Экземпляр процесса:** конкретный запуск определения процесса; имеет идентификатор и может содержать активные задачи.
- **Задача:** единица работы внутри экземпляра процесса; наблюдаемые сведения включают идентификатор, название, исполнителя и идентификатор экземпляра.
- **Пользователь:** субъект, идентифицируемый по JWT; система передаёт его идентификатор и имя в заголовках запроса к целевому сервису.

## 7. Критерии успешности и проверки

Это проверяемые критерии для описанного текущего объёма; численные целевые показатели производительности или бизнес-эффекта в проекте не заданы.

- **SC-001:** 100% запросов запуска с действительным JWT и существующим ключом определения процесса возвращают идентификатор созданного экземпляра.
- **SC-002:** 100% записей в ответе списка активных задач содержат идентификатор задачи и идентификатор экземпляра процесса.
- **SC-003:** Для активной задачи успешный запрос завершения удаляет её из результата последующего запроса списка активных задач.
- **SC-004:** 100% запросов к прикладным маршрутам без действительной аутентификации отклоняются до выполнения бизнес-операции.
- **SC-005:** Разрешённые маршруты документации доступны без аутентификации.

## 8. Допущения и вопросы для следующей части

1. Термин «оператор» используется для обозначения потребителя API задач; код не определяет роль, подразделение или отдельный пользовательский интерфейс оператора.
2. Предполагается, что ключ процесса известен вызывающей стороне и процесс заранее зарегистрирован в движке.
3. Не подтверждено, должны ли задачи быть доступны всем авторизованным пользователям или только назначенному исполнителю; текущий контроллер не ограничивает операции по исполнителю.
4. Не определены бизнес-правила проверки входных данных, формат переменных процесса, формат ошибок, повторная обработка запросов и хранение истории экземпляров.
5. Конфигурация указывает на базу H2 в памяти для сервиса процессов; долговременное хранение данных процессов не подтверждено.
6. Процесс проверки входных данных ссылается на делегат `bpmVariableValidator`, но реализация соответствующей бизнес-валидации в просмотренных исходниках отсутствует. Считать, что такой процесс успешно выполняет бизнес-проверку, нельзя.
7. Нет бизнес-метрик, SLA, ожидаемой нагрузки или целевых сроков выполнения; их следует определить отдельно, а не выводить из кода.
