# Документ функциональных требований (Functional Requirements Document — FRD)

## Проект: Платформа автоматизации процессов и процессный движок SnowSolution (Process Engine & BPMN-Driven Elicitation Platform)

---

## 1. Введение и назначение документа

Настоящий документ функциональных требований (FRD) определяет детальную функциональную спецификацию микросервисной платформы **SnowSolution**. Документ разработан на базе утвержденных бизнес-требований (BRD) и описывает конкретное поведение системы, программные интерфейсы, структуру данных, правила валидации и требования к компонентам архитектуры (Java 25, Spring Boot 3.4.2, Spring Cloud 2024.0.3, Flowable 7.1.0, Keycloak 26.0.0, PostgreSQL 16).

---

## 2. Функциональные модули и требования

### Модуль 1. Управление проектными пространствами (Project Workspace Management)

Модуль обеспечивает мультипроектную архитектуру для логического разделения бизнес-процессов и процессных воронкок по направлениям (B2B / B2C).

* **FR-PRJ-01 (Создание проекта):** Система должна предоставлять REST API и интерфейс для инициализации нового изолированного рабочего пространства. Обязательные параметры: наименование проекта, описание, привязка к каналу (B2B или B2C), инициализация изолированного контекста базы данных и прав доступа.
* **FR-PRJ-02 (Переключение контекста):** Система должна поддерживать динамическое переключение активного рабочего пространства в рамках пользовательской сессии, гарантируя, что все последующие запросы выборки задач и запуска процессов ограничены выбранным проектом.
* **FR-PRJ-03 (Архивация и удаление проекта):** Система должна позволять выполнять безопасное удаление или архивацию проекта. Перед подтверждением операции процессный движок (`process-engine-service`) обязан проверить отсутствие активных (незавершенных) экземпляров процессов в данном пространстве.

---

### Модуль 2. Сервис валидации BPMN (Validation Service)

Критический компонент обеспечения качества, реализующий методологию *BPMN-Driven Elicitation*. Проверяет машиночитаемость и полноту требований, заложенных в BPMN-схему.

* **FR-VAL-01 (Парсинг BPMN 2.0 XML):** Сервис должен программно анализировать DOM-структуру переданного BPMN-файла, извлекая узлы задач (`userTask`, `serviceTask`), шлюзов и событий, а также их дочерние элементы расширения (`extensionElements` / `camunda:properties`).
* **FR-VAL-02 (Контроль обязательных метаданных):** Сервис должен проверять наличие полного набора обязательных расширенных свойств (`extension properties`), разделенных на три блока:

1. *Target Description:* `req_id`, `feature_name`, `target_description`.
2. *Functional Requirements:* `fr_actor`, `fr_trigger`, `fr_action_logic`, `fr_expected_result`, `fr_data_contract`.
3. *Non-Functional Requirements:* `nfr_sla_ms`, `nfr_retry_allowed`, `nfr_max_retries` (условно), `nfr_security_level`, `nfr_audit_required`.

* **FR-VAL-03 (Валидация типов и форматов):**
* `req_id` должен соответствовать регулярному выражению `^REQ-[A-Z]+-\d{3}$`.
* `nfr_sla_ms` должен быть целым числом больше 0 (`> 0`).
* `nfr_retry_allowed` и `nfr_audit_required` должны содержать булевы значения (`true` / `false`).
* Если `nfr_retry_allowed = true`, поле `nfr_max_retries` становится обязательным (`integer`).
* `nfr_security_level` должен принимать одно из фиксированных значений (`PUBLIC`, `INTERNAL`, `CONFIDENTIAL`, `RESTRICTED`).
* **FR-VAL-04 (Блокировка и отчетность):** При обнаружении любых пропусков обязательных свойств или несоответствия форматов сервис должен блокировать передачу схемы в процессное ядро и возвращать структурированный JSON-отчет с перечнем ошибок и идентификаторами дефектных элементов BPMN.

---

### Модуль 3. Процессное ядро (Process Engine Service / Flowable 7.1.0)

Микросервис управления жизненным циклом бизнес-процессов.

* **FR-ENG-01 (Деплой моделей):** Сервис должен принимать предварительно валидированные BPMN 2.0 схемы и развертывать их в движке Flowable.
* **FR-ENG-02 (Запуск процессов):** Система должна предоставлять защищенный эндпоинт `POST /api/process/start` для инициализации нового экземпляра процесса по ключу шаблона.
* **FR-ENG-03 (Управление задачами):** Система должна поддерживать выборку списка активных задач (`User Task`) для текущего пользователя/роли (`GET /api/process/tasks`) и фиксацию их завершения (`POST /api/process/tasks/{taskId}/complete`) с передачей выходных переменных.
* **FR-ENG-04 (Автоматический повтор сбоев):** При возникновении ошибок на шагах интеграции движок должен считывать параметры `nfr_retry_allowed` и `nfr_max_retries` из метаданных задачи и автоматически выполнять повторные попытки выполнения (`retry`) до исчерпания лимита.

---

### Модуль 4. Шлюз API и безопасность (API Gateway & Keycloak IAM)

* **FR-SEC-01 (OAuth2 / OIDC аутентификация):** Шлюз (`api-gateway`) должен функционировать как OAuth2 Resource Server, проверяя подлинность и срок действия JWT-токенов, поступающих от сервера аутентификации Keycloak 26.0.0.
* **FR-SEC-02 (Динамическая маршрутизация):** Шлюз должен осуществлять проксирование входящих запросов к внутренним сервисам с использованием механизма обнаружения `eureka-server` (шаблон маршрутизации `/api/process/**` с фильтрацией префиксов).
* **FR-SEC-03 (Трансляция контекста):** После успешной валидации JWT шлюз обязан извлекать данные пользователя и передавать их во внутренние микросервисы в защищенных заголовках (`X-User-Id`, `X-User-Name`).

---

## 3. Спецификация контрактов данных (`fr_data_contract`)

* **FR-DAT-01 (Связывание с JSON Schema):** Каждый шаг процессной модели, требующий обмена структурированными данными, должен указывать в поле `fr_data_contract` ссылку на соответствующую JSON Schema (JSB).
* **FR-DAT-02 (Контроль контракта):** Сервис валидации BPMN должен проверять существование и доступность указанной JSON-схемы в репозитории артефактов платформы перед допуском процесса к развертыванию.

---

## 4. Требования к аудиту и мониторингу

* **FR-AUD-01 (Журналирование операций):** Для элементов процессов, у которых в нефункциональных требованиях установлено `nfr_audit_required = true`, система обязана формировать защищенную запись в системном журнале аудита. Запись должна содержать: метку времени, идентификатор пользователя (`X-User-Id`), идентификатор процесса, название шага и результат выполнения.
* **FR-MON-01 (Healthchecks):** Все микросервисы должны реализовывать эндпоинты Spring Boot Actuator (`/actuator/health`) для бесшовного мониторинга состояния инфраструктурой Docker Compose.

## 1. Архитектурный контекст и принципы взаимодействия

Платформа **SnowSolution** построена на основе распределенной микросервисной архитектуры. Все компоненты системы выделены в самостоятельные Maven-модули и развертываются в виде изолированных контейнеров Docker, взаимодействующих внутри защищенной виртуальной сети (`snow-net`).

### Требования к архитектурному взаимодействию:

* **FR-ARC-01 (Динамическое обнаружение):** Все микросервисы (`process-engine-service`, `api-gateway` и др.) обязаны при старте регистрироваться в серверном реестре (`eureka-server`) и осуществлять межсервисное взаимодействие через логические имена (динамическую балансировку).
* **FR-ARC-02 (Единая точка входа):** Любые внешние вызовы системы должны поступать исключительно через `api-gateway`, который выполняет первичную проверку подлинности, фильтрацию и маршрутизацию трафика.
* **FR-ARC-03 (Изоляция процессного ядра):** Исполнение BPMN-схем, управление экземплярами процессов и обработка задач должны быть полностью инкапсулированы в микросервисе `process-engine-service`.

## 1. Функциональные требования к пользовательским сценариям и интерфейсу сбора требований

* **FR-US-01 (Интерфейс сеанса интервьюирования и фиксации):** Система должна предоставлять графический интерфейс для взаимодействия Аналитика с Заказчиком, позволяющий в режиме реального времени создавать элементы BPMN-схем (`User Task`, `Service Task`, шлюзы, события) и напрямую заполнять их расширенные свойства (`extension properties`).
* **FR-US-02 (Структурированное хранение метаданных в XML):** Модуль моделирования обязан сохранять введенные Аналитиком метаданные (`req_id`, `feature_name`, `target_description`, блоки `fr_*` и `nfr_*`) непосредственно в тегах расширения (`extensionElements` / `camunda:properties`) стандартного файла BPMN 2.0 XML.
* **FR-US-03 (Управление жизненным циклом проектных пространств):** Система должна предоставлять интерфейс и REST API для управления проектными рабочими пространствами (создание с указанием канала B2B/B2C, переключение контекста сессии пользователя, безопасное удаление/архивация с проверкой активных экземпляров процессов).

## 2. Спецификация алгоритмов Сервиса валидации BPMN (Validation Service Specifications)

Сервис валидации выступает автоматизированным шлюзом контроля качества перед передачей моделей в исполнение процессным движком Flowable.

* **FR-VAL-10 (Алгоритм синтаксического разбора XML):** При получении запроса валидации сервис должен с использованием DOM/SAX парсеров построить дерево элементов BPMN 2.0, рекурсивно обходя все узлы задач и событий для извлечения блока `camunda:properties`.
* **FR-VAL-11 (Проверка полноты спецификаций):** Сервис обязан проверять наличие каждого из обязательных полей:

1. *Target Description:* `req_id`, `feature_name`, `target_description`.
2. *Functional Requirements:* `fr_actor`, `fr_trigger`, `fr_action_logic`, `fr_expected_result`, `fr_data_contract`.
3. *Non-Functional Requirements:* `nfr_sla_ms`, `nfr_retry_allowed`, `nfr_max_retries` (при условии `nfr_retry_allowed = true`), `nfr_security_level`, `nfr_audit_required`.

* **FR-VAL-12 (Проверка логических и условных зависимостей):**
* Если `nfr_retry_allowed` равен `true`, валидатор должен гарантировать наличие и корректность числового значения в поле `nfr_max_retries` (`integer > 0`).
* Значение `nfr_security_level` должно строго соотноситься с перечислением: `PUBLIC`, `INTERNAL`, `CONFIDENTIAL`, `RESTRICTED`.
* **FR-VAL-13 (Формирование структурированного отчета об ошибках):** В случае выявления несоответствий или пропусков сервис должен возвращать HTTP-ответ со статусом `400 Bad Request`, содержащий JSON-объект следующей структуры:

```json
{
  "status": "VALIDATION_FAILED",
  "timestamp": "2026-10-16T12:00:00Z",
  "errors": [
    {
      "elementId": "UserTask_1a2b3c",
      "elementName": "Подписание договора",
      "missingOrInvalidProperties": ["nfr_sla_ms", "req_id"]
    }
  ]
}

```

## 3. Функциональные спецификации процессных воронок B2B и B2C

* **FR-WF-01 (Изоляция потоков выполнения B2B):** Процессное ядро (`process-engine-service`) должно обеспечивать поддержку сложных структур данных (иерархия аккаунтов, вложенные подпроцессы согласования через параллельные шлюзы `Parallel Gateway`) для B2B-направления.
* **FR-WF-02 (Обработка высокоскоростных потоков B2C):** Система должна поддерживать линейные последовательные маршруты B2C с автоматическим тайм-аутом эскалации (`Timer Event`) для контроля времени реакции на запросы и бесшовной интеграцией с внешними шлюзами через сервисные задачи.

## 4. Требования к управлению экземплярами процессов и задачами

* **FR-TSK-01 (Выборка пользовательских задач):** Эндпоинт `GET /api/process/tasks` должен возвращать список задач с фильтрацией по текущему проекту, роли пользователя и статусу выполнения.
* **FR-TSK-02 (Завершение задачи и передача переменных):** Эндпоинт `POST /api/process/tasks/{taskId}/complete` должен принимать полезную нагрузку (payload) в формате JSON с выходными переменными задачи, записывать их в контекст экземпляра процесса Flowable и переводить процесс на следующий шаг.

## 1. Функциональные и системные нефункциональные требования (NFR-driven FRs)

* **FR-NFR-01 (Ограничения производительности API):** Платформа через `api-gateway` должна обеспечивать время отклика не более 500 мс для 95% стандартных запросов прикладных микросервисов (включая выборку задач и управление проектными пространствами).
* **FR-NFR-02 (Производительность процессного движка):** Микросервис `process-engine-service` должен гарантировать обработку параллельного запуска и исполнения не менее 100 экземпляров процессов в секунду на базовом стандартизированном контейнере.
* **FR-NFR-03 (Автоматический механизм повторов / Retry):** При возникновении временных сетевых или интеграционных сбоев на шаге процесса система должна считывать параметр `nfr_retry_allowed` и автоматически выполнять повторные попытки (retry) до достижения лимита, заданного в `nfr_max_retries`.
* **FR-NFR-04 (Изоляция сбоев модулей):** Архитектура должна исключать каскадные сбои: падение отдельного экземпляра процесса, ошибка валидации BPMN-схемы или сбой вспомогательного сервиса не должны приводить к деградации или остановке других микросервисов платформы.

---

## 2. Безопасность, IAM и управление доступом

* **FR-SEC-10 (Интеграция с Keycloak IAM):** Сервер **Keycloak (версия 26.0.0)** должен обеспечивать централизованную аутентификацию пользователей и выдачу JWT-токенов стандарта OAuth2 / OIDC.
* **FR-SEC-11 (Валидация токенов на шлюзе):** Микросервис `api-gateway` должен функционировать как OAuth2 Resource Server, выполняя проверку подсрочки, цифровой подписи и срока действия каждого поступающего JWT-токена.
* **FR-SEC-12 (Прозрачная трансляция пользовательского контекста):** После успешной верификации токена шлюз обязан извлекать идентификатор и имя пользователя и передавать их во внутренние микросервисы в защищенных заголовках (`X-User-Id`, `X-User-Name`).
* **FR-SEC-13 (Сетевая изоляция контура):** Все инфраструктурные и прикладные контейнеры должны функционировать внутри изолированной виртуальной сети Docker (`snow-net`), исключая прямой доступ из внешней среды к базам данных и внутренним портам сервисов.

---

## 3. Интеграционная архитектура и управление контрактами данных

* **FR-INT-01 (Динамическое обнаружение через Eureka):** Все внутренние межсервисные вызовы должны осуществляться через сервер обнаружения `eureka-server`, исключая жесткую фиксацию IP-адресов и обеспечивая балансировку нагрузки.
* **FR-INT-02 (Связывание с JSON Schema / JSB):** Каждый шаг процессной модели, требующий обмена структурированными данными, должен ссылаться на соответствующую валидируемую JSON Schema через поле `fr_data_contract` в расширенных свойствах BPMN.
* **FR-INT-03 (Автоматическая документация API):** Шлюз и микросервисы должны агрегировать спецификации REST API с помощью Springdoc OpenAPI UI (`/swagger-ui.html`), обеспечивая актуальность технической документации в реальном времени.

---

## 4. Требования к аудиту, мониторингу и эксплуатационной надежности

* **FR-AUD-10 (Защищенный системный журнал аудита):** Для элементов процессов, у которых в нефункциональных требованиях установлено `nfr_audit_required = true`, система обязана формировать защищенную неизменяемую запись в системном логе. Запись должна содержать: метку времени, идентификатор пользователя (`X-User-Id`), идентификатор экземпляра процесса, название шага и результат выполнения.
* **FR-MON-10 (Проверка состояния Healthcheck):** Все модули платформы должны реализовывать стандартные эндпоинты Spring Boot Actuator (`/actuator/health` и `/actuator/metrics`) для обеспечения контроля доступности со стороны оркестратора Docker Compose.

---

## 5. Спецификация развертывания (Deployment Specifications)

Оркестрация платформы должна осуществляться с помощью единого файла `docker-compose.yml`, объединяющего следующие компоненты:

1. **Инфраструктурный слой:**

* `snow-postgres` (PostgreSQL 16-alpine, порт `5432`)
* `snow-keycloak` (Keycloak 26.0.0, порты `8082:8080`)
* `snow-eureka` (Netflix Eureka Server, порт `8761`)

2. **Прикладной слой:**

* `snow-process-engine` (Процессный движок Flowable 7.1.0, порт `8081`)
* `snow-gateway` (API Gateway, порт `8080`)

# Документ функциональных требований (Functional Requirements Document — FRD)

## Проект: Платформа автоматизации процессов и процессный движок SnowSolution (Process Engine & BPMN-Driven Elicitation Platform)

### Часть 5: Архитектура процессного ядра, жизненный цикл экземпляров процессов, контракты данных, стратегия тестирования и дорожная карта реализации

---

## 1. Архитектура процессного ядра и управление жизненным циклом (Process Engine & Lifecycle)

* **FR-ENG-10 (Управление шаблонами процессов):** Система обязана поддерживать бесшовную загрузку, парсинг и развертывание валидированных BPMN 2.0 схем в процессный движок Flowable 7.1.0 с извлечением всех расширенных свойств (`extension properties`).
* **FR-ENG-11 (Жизненный цикл задач):** Система должна поддерживать строгую модель состояний для пользовательских и сервисных задач:

1. *Created (Создана):* Генерация задачи движком при активации узла схемы.
2. *Assigned (Назначена):* Закрепление задачи за конкретным оператором или группой ролей.
3. *Completed (Завершена):* Успешное выполнение с фиксацией выходных переменных в контексте процесса.
4. *Failed / Retry (Ошибка / Повтор):* Автоматическая обработка сбоев интеграции на основе параметров `nfr_retry_allowed` и `nfr_max_retries`.

* **FR-ENG-12 (Поддержка процессных воронок B2B и B2C):** Движок должен корректно обрабатывать сложные многоуровневые цепочки с параллельными шлюзами (`Parallel Gateway`) для корпоративных процессов, а также высокоскоростные линейные потоки с таймерами эскалации (`Timer Event`) для массовых операций.

---

## 2. Управление контрактами данных (`fr_data_contract`)

* **FR-DAT-10 (Привязка JSON Schema):** Каждый шаг процессной модели, предусматривающий обмен структурированными данными, должен ссылаться на верифицируемую JSON Schema через поле `fr_data_contract` в метаданных BPMN-элемента.
* **FR-DAT-11 (Проверка контрактов на этапе валидации):** Сервис валидации BPMN должен программно проверять наличие и доступность указанной JSON-схемы в репозитории артефактов платформы до допуска процессной модели к деплою.

---

## 3. Стратегия тестирования и обеспечение качества

Для гарантии стабильности микросервисного контура платформа должна удовлетворять следующим требованиям к тестированию:

* **FR-TST-01 (Модульное тестирование / Unit Tests):** Все компоненты бизнес-логики, парсеры XML-структур BPMN и валидаторы должны покрываться модульными тестами с использованием JUnit 5 и Mockito.
* **FR-TST-02 (Интеграционное тестирование с Testcontainers):** Интеграционные тесты взаимодействия с процессным движком и базой данных PostgreSQL должны выполняться с автоматическим поднятием изолированных контейнеров через Testcontainers.
* **FR-TST-03 (Автоматизированный пре-релизный контроль):** Конвейер сборки обязан автоматически инициировать проверку всех BPMN-шаблонов через Сервис валидации BPMN перед формированием релизных артефактов.

---
